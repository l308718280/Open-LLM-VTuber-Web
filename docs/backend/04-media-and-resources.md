# 多媒体与 HTTP 资源

## 1. 音频输入：先确定格式，再对接 ASR

已核实：前端 VAD 在一句话结束后拿到完整浮点样本，再以最多 4096 样本一片连续发送 JSON 数组，最后发送结束消息和图片。不是持续实时逐帧推送，不能按实时流协议等待固定片间隔。依据：[`vad-context.tsx`](../../src/renderer/src/context/vad-context.tsx:231)、[`use-send-audio.tsx`](../../src/renderer/src/hooks/utils/use-send-audio.tsx:11)。

待确认：有效采样率、声道、样本数值范围，以及 VAD 依赖是否已重采样。当前没有采样率字段，不能把浏览器设备采样率直接当 ASR 输入采样率，也不能未经验证固定宣称为 16 kHz。实施前读取锁定依赖实现，录制已知时长音频，以样本总数除以时长交叉验证，并实际回放和识别。

后端建议：

- 接收有限数值，拒绝非数值、非有限数值、超长数组和超过已确认范围的输入；不要把异常值静默转零。
- 使用原始浮点数组或受限缓冲，避免长期存储装箱数值列表和整份 JSON 树；同时限制片数、总样本、上传总字节和持续时间。
- 需要转 PCM16 时，先确认输入归一化范围，再裁剪和量化，声明正确采样率、声道及小端字节序。重采样用可靠库，不靠简单跳点。
- 未完成上一段时不能接受两段音频交错。旧协议没有上传 ID，首片与结束之间的超时或取消必须明确清理；无法可靠识别残留分片时关闭连接或要求重新采集。
- 客户端没有逐片 ACK，也未实现服务端流控反馈；超限返回错误后可关闭连接，不能继续无界缓冲。

## 2. 音频输出：每段都是独立可解码文件

前端把输出拼成 WAV Data URL，因此每段必须是含完整文件头的 WAV 的裸 Base64，而不是 PCM 原始字节、MP3 改 MIME、带前缀的 Data URL，或完整 WAV 的任意字节切片。播放与口型分析都要验证所选编码；建议先以普通 PCM WAV 建立闭环。

按句合成以降低首音等待，处理中文标点、代码块、缩写和长句；没有标点也应在受限长度或等待时间后切段。并行合成需保序，空句跳过，失败句可用纯文字降级。文本展示只能追加一次。

当前音量数组和切片长度虽然传入播放选项，但播放口型由 WAV 分析驱动，不能把填充音量数组当成口型实现。表情只消费数组首项，必须与当前模型的表情映射一致；图片和声音动作字段不能因为已声明就视为功能完成。依据：[`use-audio-task.ts`](../../src/renderer/src/hooks/utils/use-audio-task.ts:107)。

播放失败、无模型、用户未授予音频播放权限都不能无限阻塞服务端。建议保存生成/发送状态，播放回执仅作为提示，配合总超时和降级。取消时回收转码进程、流、临时文件和句子缓冲。

## 3. 容量预算与限制

以下是公式和示例，不是当前已测配置：

- 单声道浮点缓冲字节约为采样率 × 秒数 × 4。若最终确认 16 kHz，则 30 秒约 1.92 MB；JSON 浮点字符串通常更大，必须按实际序列化测量。
- PCM16 WAV 主体约为采样率 × 声道数 × 秒数 × 2，再加文件头。Base64 长度为 4 × 向上取整（二进制字节数 / 3），还需加 JSON 文本字段开销。
- 峰值内存同时包含上传字符串、解析对象、浮点缓冲、TTS 二进制及 Base64、发送队列、图片解码像素；不要只预算最终音频文件大小。
- WS 容器的文本消息上限、应用校验、代理限制及供应商上限必须一致。图片结束消息和单句音频通常比单个采样分片大，不能仅按 4096 样本估算整个接口的上限。

把最大语音秒数、图片字节/像素数、单轮图片数、单句音频字节、每连接待发字节及全局并发设为集中配置。先测典型与极端场景再定数值；过载时明确拒绝，不能仅依赖堆内存耗尽作为保护。

## 4. 图片与隐私

当前摄像头和屏幕是按请求截 JPEG 图，不是持续上传视频。图片包含来源、JPEG Data URL 和 MIME，见 [`use-media-capture.tsx`](../../src/renderer/src/hooks/utils/use-media-capture.tsx:22)。无可用流时为空数组；文字发送、语音结束、主动说话均可能携带图片。

后端检查前缀、Base64、真实图片格式、数量、压缩字节、宽高和总像素，解码前后都限制资源，防止解压炸弹。不要根据客户端 MIME 直接信任内容，不把 Data URL 当网络 URL 请求。图像不受支持时明确选择拒绝或告知降级，不能声称看到了实际上未送入模型的画面。

采集到的屏幕可能含聊天、口令或公司资料。默认仅本轮处理，不记录原图和 Data URL，不自动转发群组；外部模型处理前应明确供应商、用途和保留政策。需要留存时增加授权、访问控制、保留期限及删除机制。

## 5. HTTP 与 Live2D 资源发布

固定资源依赖和动态加载点见 [`backend.md`](../backend.md:142)。保留默认背景路径、头像目录以及模型配置引用的完整相对目录结构，不能只发布主配置而遗漏纹理、模型二进制、动作或物理文件。

- 基础地址建议不以斜杠结尾，返回的站内模型和背景路径以斜杠开头；这是部署约定，需与直接字符串拼接代码验证。头像值返回受控相对文件名，不返回已带头像目录的绝对地址。
- 模型主配置内的子资源保持相对路径，并对目录大小写、中文、空格编码和 Linux 文件系统差异逐项检查。
- JSON、JPEG/PNG、WAV、二进制资源返回正确 MIME。缺失文件返回 404，不回退为 SPA 首页或登录 HTML；可选文件缺失按 SDK 实际行为验收。
- 带版本路径的公开模型资产可长期缓存；角色列表和可变配置使用短缓存或验证缓存。更新主配置和子资源应原子发布或使用版本目录。
- 跨域 fetch 和匿名纹理加载需要适当 CORS；凭据资源不能使用通配 Origin。当前部分加载路径不携带跨站凭据，优先公开非敏感资产或同源代理；不能只配置 Cookie 就假设所有 SDK 加载都能认证。
- 路径正规化后限制到资源根目录，检查符号链接逃逸；禁用目录列表，不发布角色密钥、数据库配置或用户上传的任意可执行内容。

VAD 与 ONNX/WASM 的本地库资源属于前端部署资源，应同步检查是否随前端发布；不是 Java 自动提供的 ASR 模型。HTTPS 页面需要 WSS 和 HTTPS 资源，避免混合内容阻止加载。
